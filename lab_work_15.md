Практична робота №15
Створення індексів та аналіз ефективності запитів

База даних: Автосалон.

Фактова таблиця: sales.

Завдання 1. EXPLAIN QUERY PLAN до індексу

Для перевірки плану виконання запиту використано зовнішній ключ customer_id таблиці sales.

Запит:

sql
EXPLAIN QUERY PLAN
SELECT * FROM sales
WHERE customer_id = 1;


Результат: SCAN sales (вставити фактичний результат SQLite).

SQLite виконує повний перегляд таблиці та перевіряє кожен запис на відповідність умові.

Завдання 2. CREATE INDEX на зовнішньому ключі

Створено індекс на колонці customer_id:

sql
CREATE INDEX idx_sales_customer
ON sales(customer_id);


Після створення індексу повторно виконано запит.

Результат: SEARCH sales USING INDEX idx_sales_customer (customer_id=?) (вставити фактичний результат).

План змінився з SCAN на SEARCH USING INDEX. SQLite тепер використовує індекс для пошуку записів за ідентифікатором клієнта.

Завдання 3. Композитний індекс

Для пошуку продажів використано дві умови: customer_id та car_id.

Створено композитний індекс:

sql
CREATE INDEX idx_sales_customer_car
ON sales(customer_id, car_id);


До створення композитного індексу використовувався одноколонковий індекс customer_id.

Після створення композитного індексу SQLite отримала можливість використовувати обидві колонки для пошуку.

Композитний індекс є ефективнішим для запитів, у яких одночасно використовуються обидві колонки, оскільки дозволяє звузити пошук за двома умовами.

Завдання 4. Індекс і ORDER BY

Для сортування продажів за датою створено індекс:

sql
CREATE INDEX idx_sales_date
ON sales(sale_date);


До створення індексу план містив крок USE TEMP B-TREE FOR ORDER BY.

Після створення індексу SQLite почала використовувати впорядковану структуру індексу для отримання записів.

Окремий крок сортування зник. Це дозволяє уникнути додаткової операції сортування.

Завдання 5. DROP INDEX і повторна перевірка

Видалено одноколонковий індекс:

sql
DROP INDEX idx_sales_customer;


Після видалення повторно перевірено план запиту за customer_id.

SQLite може використовувати композитний індекс idx_sales_customer_car, оскільки він починається з колонки customer_id.

Додатково виконано запит до sqlite_master:

sql
SELECT name, tbl_name
FROM sqlite_master
WHERE type = 'index';


Перевірка підтверджує, що індекс idx_sales_customer видалений, а інші індекси залишилися.

Контрольні питання

1. Чому EXPLAIN QUERY PLAN показує саме план, а не результат запиту, і навіщо перевіряти план окремо від того, що запит просто працює?

EXPLAIN QUERY PLAN показує спосіб, яким SQLite планує виконати запит, а не самі дані. Це дозволяє зрозуміти, чи виконується повний перегляд таблиці SCAN, чи використовується індекс SEARCH. Запит може повертати правильний результат, але виконуватися повільно. Тому важливо перевіряти не лише правильність результату, а й ефективність виконання.

2. Чому індекс лише на першій із двох колонок дає менший ефект, ніж композитний індекс на обох?

Індекс на одній колонці дозволяє знайти записи за першою умовою, але другу умову SQLite перевіряє додатково. Композитний індекс містить обидві колонки та дозволяє використовувати обидві умови безпосередньо під час пошуку. Тому він ефективніший для запитів із двома умовами.

3. Яка ціна створення індексу і чому не варто індексувати кожну колонку таблиці?

Індекс займає додаткове місце на диску та потребує часу для створення. Крім того, під час INSERT, UPDATE і DELETE SQLite повинна оновлювати відповідні індекси. Через це збільшується час виконання операцій запису та розмір бази даних. Тому індекси потрібно створювати лише на колонках, які часто використовуються для пошуку, з'єднання таблиць і сортування.
